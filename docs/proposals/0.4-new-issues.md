## 1. Show the UI flow before building

**The gap.** We planned behaviour in detail but never showed what the platform *looks like*. The lead and the client can't react to tables of rules.

**Proposal: Phase 0.5, "UI flow" (docs only, before the 9 Oct call).**

- One flow diagram per role: what each person clicks through, screen by screen. Roles: applicant, staff (including the page builder), jury (document and on-site), department head / organiser, leader and PA.
- Simple wireframes (grey boxes, no colours) for the key screens: the public award site, the page builder, the application form, the jury scoring screen, the staff dashboard, the leader dashboard.
- Delivered as Markdown plus a screen-share page in `docs/overview/`, like the 0.3 overview.
- **Why wireframes, not a designed UI:** they are fast, they keep the discussion on *flow* rather than colours, and nothing is thrown away when the design changes.

## 2. Branded award sites (the big one)

### What the organiser has today

The FPO Awards page (face-cii.in/fpo-awards, designed by ColoredCow) is built from about ten standard sections:

1. A banner with the deadline and an **Apply** button
2. Eligibility
3. About the programme
4. Objectives (icon cards)
5. Award categories (icon cards)
6. The award process (a flowchart)
7. A photo gallery
8. **Past winners**, filterable by year, category, state and commodity
9. Contact people
10. A footer with social links

Applications go to a **separate portal** (awards.ciifpoprogram.com). That is the real problem today: the brand lives on one website, the applications in another system, and the data in a third place.

### How other platforms solve this

These are general patterns, worth checking against each product's current features before quoting them:

- **Website builders** (Squarespace, Wix, Webflow-style "sections"): you pick a section type (hero, gallery, FAQ…) and fill it in. The platform guarantees it looks good on every screen.
- **Award-management software** (Award Force, Submittable, OpenWater and similar): each programme gets a **branded portal** with its logo, colours, banner and its own pages. Some offer a custom domain.
- **Event platforms** (Eventbrite, Luma): one rich page per event, built from structured fields plus images, with share previews for social media.

The common pattern is **structured sections plus a theme**. None of them give organisers raw HTML: it breaks layouts, is unsafe (scripts can steal logins), and can't be checked for accessibility.

### Proposed design

```
Department (the organiser)
 └─ Brand kit ─────────── logo, colours, fonts (from a safe list), social links, footer text
     └─ Award site ─────── one per award; uses the brand kit, can override colours and banner
         ├─ Pages ──────── Home, plus extra pages (e.g. "Categories", "Past winners", "Gallery")
         │   └─ Sections ─ ready-made blocks, filled in by staff
         └─ Address ────── platform path now; sub-domain or own domain later (§5)
```

**Section types** (from the FPO page and common practice):

| Section | Filled by staff | Filled automatically from the platform |
|---|---|---|
| Banner | Title, tagline, image | The deadline and the **Apply** button (correct, always) |
| Rich text | Headings, paragraphs, lists, links | — |
| Icon cards | Objectives, benefits | — |
| Categories | Short description and icon per category | The category names and fees of the open cycle |
| Eligibility | Text and bullet points | — |
| Process / timeline | Steps | The key dates of the cycle |
| Photo gallery | Uploaded images with captions | — |
| Past winners | (just switch it on) | **Published results** of earlier cycles: year, category, label (Gold, Shortlisted…), organisation |
| Jury | (optional, switch on) | Jury names the organiser chooses to show; never in a blind award while judging runs |
| Partners / sponsors | Logos and links | — |
| FAQ | Questions and answers | — |
| Contacts | Names, emails | — |

The **automatic sections are the big advantage over a normal website**. The deadline, categories and past winners always match the real data, so the data stays consistent: no copy that someone forgets to update.

**Guardrails (why staff get freedom but can't break anything):**

- **No custom HTML or scripts.** Rich text allows bold, italic, headings, lists and links only.
- **Colours** are picked from the brand kit, and the editor warns when text would be hard to read (contrast check).
- **Images:** JPG, PNG or WebP, up to 5 MB, resized automatically for phones, **alt text required** for accessibility.
- **Draft → preview → publish**, like the questionnaire: a published page is an immutable version, so the live site never shows half-edited content. Every publish is audited.
- **Public files are kept apart** from applicants' private documents (a separate public storage bucket), so a page image can never expose an application file.
- **Share preview:** each page has a title, description and image for Google, WhatsApp and LinkedIn previews. That helps promotion.

**Who can edit:** the award's staff and its department head. The leader and PAs can see every site. Whether a site needs the leader's approval before it goes live is question J5.

### What it changes

- **Data model (new tables):** `BrandKit` (per department), `AwardSite`, `SitePage`, `SitePageVersion` (immutable, like `FormVersion`), `MediaAsset` (public images).
- **Backend:** a new `sites` module, plus a public read API for published pages.
- **Frontend:** the public award site renderer (fast, cached, SEO-friendly; Next.js is good at this) and the **page builder** for staff.
- **Plan:** two new build phases (§6).

### What we would NOT build in the 10 days (proposal)

- Drag-and-drop free layout (sections are reordered with up/down arrows instead).
- Custom fonts uploaded by organisers (a safe font list instead).
- Own domains (designed for, §5).
- Analytics on page visits.

## 3. Organisers run their own award

**The flow the owner described:** an organisation that runs an award comes to our leader → the leader creates a **department** for it → appoints the organiser's person as **department head** → that person adds their own staff, chooses their own jury, builds their award site, and runs everything without going back to the leader. They see only their department's data; the leader (and PAs) see everything.

**This mostly fits the design already:**

| Need | Already in the design? |
|---|---|
| Leader creates the department and appoints its head | ✅ spec §5.3 |
| Department head adds staff, staff create awards | ✅ |
| Department head and staff choose the jury pool | ✅ |
| Department head sees only their department | ✅ scopes on every role |
| Leader sees everything, read-only | ✅ |
| The department's own dashboard | ⚠️ was "could have"; becomes **must have**, because organisers work independently |
| The department owns its brand (brand kit) | ❌ new (§2) |
| A department head who is not part of the industry body | ⚠️ new meaning: "department" can be an **external organiser**. The spec's glossary needs one line on this |

**Points to settle (questions J3 and J4):** whether department heads should also be able to create awards themselves (today only staff can), and whether one person can head more than one department.

## 4. One entry per organisation, entry limits, and verification

### One entry per organisation (kept)

Already the rule: one real application per organisation per award cycle; every application is accepted, extras are flagged, and staff keep one. The owner confirms it stays.

### Entry limit (new)

Staff can set an **optional maximum number of entries** for a cycle (e.g. 200). Proposal:

- Counts **submitted** applications (not drafts, not withdrawn, not rejected-as-duplicate). An organisation's flagged duplicates count **once**, so fake extra entries can't use up places.
- When the limit is reached, new submissions are refused with "This award has reached its entry limit". Drafts stay saved, and staff can raise the limit.
- The public site shows "X places left" only if staff switch it on (J7).

### Proof that the applicant works for the organisation (new)

This brings back a *verification* step, but **not** the old signed authorisation letter (ADR 0007): nothing to sign, no template.

- When a person **joins an organisation** on the platform, they add their **LinkedIn profile link** and upload one **proof of employment**: an employee ID card, a letter on company letterhead, or similar.
- **Staff check it** (LinkedIn can't be checked automatically, because its API is closed to this use) and mark the membership **Verified** or **Rejected** with a reason. It's audited.
- The check is **per person per organisation, not per application**, so it's reused for every award they apply to. That's data consistency again, and much less work for staff.
- **Duplicates get easier:** when two people from the same organisation apply, staff can see which one is verified.

**Privacy (India's DPDP Act 2023):** these are personal documents.

- Ask for the **least** we need: an ID card or a letter is enough. Tell applicants to **hide salary** details.
- Say clearly why we ask, and get consent at upload.
- Only the award's staff, the department head, the leader and PAs can see them. **Never jury** (it would also break blind judging).
- Keep them only as long as needed: proposal, until the cycle's results are published plus 12 months, then delete the document and keep the "Verified on <date> by <staff>" record. That is a deliberate, written exception to "nothing is ever hard-deleted" (J8).

## 5. Own domain: how an organiser's award can stand out

| Option | Example address | What it takes | Proposal |
|---|---|---|---|
| A. Platform path | `ourplatform.in/awards/fpo` | Nothing extra | **Build now** |
| B. Sub-domain | `fpo.ourplatform.in` | One wildcard DNS entry on a domain we own, plus Next.js reading the host name | **Design now, build after the 10 days** |
| C. Organiser's own domain | `fpoawards.in` | The organiser adds one DNS record (CNAME); the platform registers the domain with Vercel through its API; HTTPS is automatic | **Later**, per organiser, on request |
| D. Keep their website, link to us | Their own site → "Apply" goes to our branded apply page | Nothing; works today | **Always possible** |

- **Why not build B/C now:** they need a domain we own, Vercel domain settings, and a test with real DNS. None of that can be checked inside the 10-day build, and the free `vercel.app` address can't hold sub-domains.
- **What we build now so B/C are cheap later:** every award site gets a unique short name (its *slug*, e.g. `fpo`) and an empty `customDomain` field. Adding a domain later is configuration, not new code.
- The organiser's brand stands out through the brand kit, the banner, their own pages, past winners and share previews. **The address is the least important part.**
